# セルフホスト運用ガイド

対象: 現在の M3 API。これは運用設計と訓練の手順であり、HA・SLA・復旧性能の検証済み宣言ではない。導入の配線は [組み込みガイド](embedding.md)。`examples/standalone` はデモであり、そのまま本番運用する配布物ではない。

## 構成と責任

- `PublicHandler()` は TLS 終端・レート制限の内側に公開する。`InteractionHandler()` は内部ネットワークのみに配置し、バックチャネル認証（`InteractionAuth`）も必須にする。
- 本番で `storage/memory` やデモの自動承認を使わない。複数ノードは PostgreSQL を共有し、同じ `Issuer`・Client / Resource の設定・鍵セットを配布する。
- DB・署名鍵・Interaction の資格情報を別々に保護する。プロセス権限とバックアップ復号権限を最小化し、認証情報をソース・ログへ含めない。
- アプリ担当はユーザー認証・同意・業務認可、運用担当は TLS・DB・鍵・監視・復旧、保守者はエンジンの不具合修正を担当する。窓口と当番は導入時に実名で決める。

## 出荷前の確認

[組み込みガイドの本番チェック](embedding.md#9-本番に出す前の確認) に加え、以下をステージングで実行し、構成・版・結果・担当・所要時間を記録する。

| 試験 | 操作 | 受入条件 |
| --- | --- | --- |
| ノード障害 | 2 ノードの一方を停止 | 残ノードで既存の Code 交換・Refresh が正しく動く。リプレイを許さない |
| DB 障害 | DB 接続を遮断 | 認証を迂回せず失敗。readiness は失敗し、復旧後に正常化 |
| 鍵更新 | 下記の段階的更新 | 全ノードで新旧トークンの検証が期待どおり |
| 復元 | 隔離環境でバックアップ復元 | データ・鍵の整合と失効方針を確認。RTO / RPO を実測 |
| 更新 | 旧版から新版へ移行 | 新旧ノード混在の可否、移行前バックアップ、撤退手順を確認 |
| 負荷 | 実運用比率で Code / Refresh / client_credentials / Introspection | p95 / p99、成功率、DB 待ち、CPU / RAM、持続時間を記録 |

計測対象には DB の版、CPU、ストレージ、ネットワーク、Access Token の形式、接続数、データ件数、warm / cold を含める。条件なしの「毎秒何万件」を公表しない。

## 観測とアラート

現在は構造化ログが中心で、イベントの一覧は [組み込みガイド §8](embedding.md#8-ログと監査) にある。health / metrics のエンドポイントはエンジンにないので、組み込み側で実装する。readiness は短い期限付きの DB 疎通と設定・鍵の準備を確認し、内部だけに公開する。liveness は DB 障害に連動させず、再起動ループを起こさない。履歴のないメトリクスから稼働保証を導かない。

| 信号 | 対応 |
| --- | --- |
| `http.internal_error`、5xx の増加 | DB 接続・直前のリリース・鍵設定を確認し、必要ならトラフィックを縮退 |
| `code.reuse` / `refresh.reuse` | 対象 Client と時刻を確認。クライアントの二重送信と漏洩を切り分け、再認可を案内 |
| `refresh.client_mismatch`、`resume.denied` の急増 | 不正アクセス・設定不一致・Cookie 設定を調査 |
| `token.rejected` の増加 | `error` 属性でプロトコルエラーとサーバー障害を分け、Client の設定やレート制限を確認 |
| `Store.Purge` の失敗、DB 容量・接続待ちの増加 | ジョブと DB を調査。失効・再利用検知の保持期間を理解せずに行を直接削除しない |
| `config.insecure_issuer` / `config.insecure_cookies` / `config.cimd_allow_loopback` | 開発用の緩和が有効。本番リリースを停止し、安全な設定に修正 |

メトリクスのラベルはエンドポイント・ステータスクラス・grant_type など有限の集合に制限する。トークン、Code、Resume URL、シークレット、Authorization ヘッダー、ユーザー ID、自由入力をラベルにしない。アクセスログは URL の query を除外し、アプリの自由入力や DB エラーに個人情報がないか確認する。保存期間と閲覧権限は顧客要件で決める。

可用性の分母・分子（正常要求の成功、想定 4xx の除外、5xx / timeout の計上）を定義し、窓長・目標・アラート閾値を実測後に決める。ログ出力だけでは改ざん耐性のある監査台帳にはならない。必要な場合は外部保管・アクセス制御・欠損検知を設ける。

## 鍵ローテーション

1. 現在の鍵、最大トークン寿命、JWKS キャッシュ期間、時計ずれ許容を記録する。安全なバックアップを確保する。
2. 新しい鍵を `keys.Generate` で作り、`Set.AddVerification` で**検証鍵として**全ノードへ先行配布する。この時点では署名に使わず、`/jwks` に公開鍵が載るだけにして、署名切替前にキャッシュ更新の猶予を取る。
3. `Set.AddSigning` で新鍵を署名鍵へ切り替える。旧鍵は検証鍵として残る。`ExportPrivate` / `ImportPrivate` による保存と、配布・再起動の手順を隔離環境で確認する。
4. 全ノードの新鍵使用と新旧トークンの検証を確認する。ノード間で鍵セットが違う状態を放置しない。
5. 最後の旧鍵発行から最大寿命＋時計ずれ・キャッシュの猶予が過ぎた後に、`Set.Remove` で旧鍵を外し、保存データも更新する。

鍵 API の使い方は [keys の例](../keys/example_test.go)。現状に自動配布・自動ローテーションの機構はない。鍵侵害時は通常更新とは別に、JWT の期限と Resource Server のキャッシュが影響するため、対象 Resource Server 側も含めて旧鍵拒否・再認可を調整する。

## バックアップと復旧

DB と暗号化した鍵・設定を復元可能にする。PITR を利用する場合も復元訓練を省略しない。復旧時刻、最終バックアップ時刻、失われる更新の範囲を記録する。

**過去の DB 復元は、失効済みトークンや消費済みの Code / Refresh Token を再び有効に戻す可能性がある。** DB が起動しただけで公開を再開しない。

1. 発行・更新トラフィックを止め、バックアップを隔離環境へ復元する。
2. DB・鍵・設定の整合、必要な migration、Client / Resource の情報を確認する。
3. 復元点以降の失効・消費情報を信頼できる手段で復元できなければ、復元された認可状態を引き継がず、全セッションの再認可を選ぶ。現在の API に全トークンの一括無効化操作はないため、検証済みの再構築手順を先に用意する。未検証の SQL を本番で実行しない。
4. Opaque の DB 失効と JWT のローカル検証を区別する。署名鍵の変更だけでは Opaque の Access Token は無効にならず、DB の失効だけでは JWT のローカル検証は止まらない。必要な鍵拒否・キャッシュ更新を Resource Server と調整する。
5. canary で Code + PKCE、Refresh Token の再利用検知、旧トークンの拒否、audience の検証を確認して段階的に再開する。
6. 実際の RTO / RPO、影響ユーザー、データ欠損を記録する。定期訓練と DB / 鍵 / 移行の変更時に再検証する。

## 障害・脆弱性対応

初動では担当者・発生時刻・影響範囲を記録し、機密値を除いた証跡を保存する。トークン盗用の疑いでは対象の Grant / Token Family の失効と再認可を検討する。署名鍵侵害は上記の JWT 対策も必要。復旧後に原因、検知の遅れ、再発防止、期限と担当を記録する。

脆弱性の報告は [SECURITY.md](../SECURITY.md)。一般の問い合わせと機密の報告を混同しない。
