# セルフホスト運用ガイド

対象: 現在のM3 API。これは運用設計と訓練の手順であり、HA・SLA・復旧性能の検証済み宣言ではない。導入の配線は [組み込みガイド](embedding.md)。`examples/standalone` はデモであり、そのまま本番運用する配布物ではない。

## 構成と責任

- PublicHandlerはTLS終端・レート制限の内側に公開する。InteractionHandlerは内部ネットワークのみに配置し、バックチャネル認証も必須にする。
- 本番でmemory Storeやauto-approveを使わない。複数ノードはPostgreSQLを共有し、同じissuer・client/resource設定・鍵セットを配布する。
- DB・署名鍵・Interaction資格情報を別々に保護する。プロセス権限とバックアップ復号権限を最小化し、認証情報をソース・ログへ含めない。
- アプリ担当はユーザー認証・同意・業務認可、運用担当はTLS・DB・鍵・監視・復旧、保守者はエンジンの不具合修正を担当する。窓口と当番は導入時に実名で決める。

## 出荷前の確認

[組み込みガイドの本番チェック](embedding.md#9-本番に出す前の確認) に加え、以下をステージングで実行し、構成・版・結果・担当・所要時間を記録する。

| 試験 | 操作 | 受入条件 |
| --- | --- | --- |
| ノード障害 | 2ノードの一方を停止 | 残ノードで既存のCode交換・Refreshが正しく動く。リプレイを許さない |
| DB障害 | DB接続を遮断 | 認証を迂回せず失敗。readinessは失敗し、復旧後に正常化 |
| 鍵更新 | 下記の段階的更新 | 全ノードで新旧トークンの検証が期待どおり |
| 復元 | 隔離環境でバックアップ復元 | データ・鍵の整合と失効方針を確認。RTO/RPOを実測 |
| 更新 | 旧版から新版へ移行 | 新旧ノード混在の可否、移行前バックアップ、撤退手順を確認 |
| 負荷 | 実運用比率でCode/Refresh/M2M/Introspection | p95/p99、成功率、DB待ち、CPU/RAM、持続時間を記録 |

計測対象にはDB版、CPU、ストレージ、ネットワーク、token形式、接続数、データ件数、warm/coldを含める。条件なしの「毎秒何万件」を公表しない。

## 観測とアラート

現在は構造化ログが中心。health/metricsは組み込み側で実装する。readinessは短い期限付きDB疎通と設定・鍵の準備を確認し、内部だけに公開する。livenessはDB障害に連動させて再起動ループを起こさない。履歴のないメトリクスから稼働保証を導かない。

| 信号 | 対応 |
| --- | --- |
| `http.internal_error`、5xx増加 | DB接続・直前のリリース・鍵設定を確認し、必要ならトラフィックを縮退 |
| `code.reuse` / `refresh.reuse` | 対象clientと時刻を確認。クライアントの二重送信と漏洩を切り分け、再認可を案内 |
| `refresh.client_mismatch` / `resume.denied`急増 | 不正アクセス・設定不一致・Cookie設定を調査 |
| `token.rejected`の増加 | protocol errorとサーバー障害を分け、clientの設定やレート制限を確認 |
| Purge失敗・DB容量・接続待ち増加 | ジョブとDBを調査。失効・再利用検知の保持期間を理解せず直接削除しない |
| `config.insecure_*` | 本番リリースを停止し、安全な設定に修正 |

メトリクスのラベルはendpoint・status class・grant typeなど有限の集合に制限する。token、Code、Resume URL、secret、Authorizationヘッダー、ユーザーID、自由入力をラベルにしない。アクセスログはURLのqueryを除外し、アプリの自由入力やDBエラーに個人情報がないか確認する。保存期間と閲覧権限は顧客要件で決める。

可用性の分母・分子（正常要求の成功、想定4xxの除外、5xx/timeoutの計上）を定義し、窓長・目標・アラート閾値を実測後に決める。ログ出力だけでは改ざん耐性のある監査台帳にはならない。必要な場合は外部保管・アクセス制御・欠損検知を設ける。

## 鍵ローテーション

1. 現在の鍵、最大トークン寿命、JWKSキャッシュ期間、時計ずれ許容を記録。安全なバックアップを確保する。
2. 新しい鍵の**公開鍵**を全ノードのJWKSへ先行配布する。`keys.Set`の検証鍵として追加するAPIを使い、署名切替前にキャッシュ更新の猶予を取る。
3. 新鍵を署名鍵へ切り替え、旧鍵は検証鍵として残す。`AddSigning` / `ExportPrivate`と配布・再起動の手順を隔離環境で確認する。
4. 全ノードの新鍵使用と新旧tokenの検証を確認する。ノード間で鍵セットが違う状態を放置しない。
5. 最後の旧鍵発行から最大寿命＋時計ずれ・キャッシュの猶予が過ぎた後に旧鍵を削除し、保存データも更新する。

鍵APIの使い方は [keysの例](../keys/example_test.go)。現状に自動配布・自動ローテーションの機構はない。鍵侵害時は通常更新とは別に、JWTの期限とResource Serverのキャッシュが影響するため、対象Resource Server側も含めて旧鍵拒否・再認可を調整する。

## バックアップと復旧

DBと暗号化した鍵・設定を復元可能にする。PITRを利用する場合も復元訓練を省略しない。復旧時刻、最終バックアップ時刻、失われる更新の範囲を記録する。

**過去のDB復元は、失効済みtokenや消費済みCode/Refreshを再び有効に戻す可能性がある。** DBが起動しただけで公開を再開しない。

1. 発行・更新トラフィックを止め、バックアップを隔離環境へ復元する。
2. DB・鍵・設定の整合、必要なmigration、client/resource情報を確認する。
3. 復元点以降の失効・消費情報を信頼できる手段で復元できなければ、復元された認可状態を引き継がず全セッション再認可を選ぶ。現在のAPIに全token一括無効化操作はないため、検証済みの再構築手順を先に用意する。未検証のSQLを本番で実行しない。
4. OpaqueのDB失効とJWTのローカル検証を区別する。署名鍵の変更だけでOpaque tokenは無効にならず、DBの失効だけでJWTのローカル検証は止まらない。必要な鍵拒否・キャッシュ更新をResource Serverと調整する。
5. canaryでCode+PKCE、Refresh再利用、旧token拒否、audience検証を確認して段階的に再開する。
6. 実際のRTO/RPO、影響ユーザー、データ欠損を記録する。定期訓練とDB/鍵/移行変更時に再検証する。

## 障害・脆弱性対応

初動では担当者・発生時刻・影響範囲を記録し、機密値を除いた証跡を保存する。トークン盗用の疑いでは対象Grant/Familyの失効と再認可を検討する。署名鍵侵害は上記のJWT対策も必要。復旧後に原因、検知の遅れ、再発防止、期限と担当を記録する。

脆弱性の報告は [SECURITY.md](../SECURITY.md)。一般の問い合わせと機密の報告を混同しない。
